# StatefulSets and headless DNS

*Stage 3 · Mission Data*

Stateless web APIs treat individual Pods as fungible, disposable workers. If `booking-68697c-xkf2p` dies, the ReplicaSet launches `booking-68697c-9m4lz`. The new Pod has a completely different name, a different IP, and no expectation of inheriting previous local files. Callers never notice because a standard Service load-balances across whatever Pods happen to be ready.

**Distributed databases, consensus clusters, and datastores break this model entirely.**

A PostgreSQL primary-replica cluster, a Redis Sentinel setup, or an Apache Kafka broker requires:
- **Deterministic identity**: Node 0 must always be Node 0, maintaining its role across reboots.
- **Sticky dedicated storage**: When Node 0 dies and is recreated, it must remount the *exact same disk* containing its transactional write-ahead logs (WAL).
- **Direct addressability**: Standbys must connect specifically to the primary replica to stream replication logs, rather than hitting a randomized round-robin virtual IP.
- **Ordered initialization**: Node 0 (the primary) must initialize its database and accept connections before Node 1 and Node 2 boot and replicate.

Kubernetes provides **`StatefulSet` (`apps/v1`)** and **Headless Services (`clusterIP: None`)** to satisfy these exact distributed systems contracts.

---

## Architectural contrast: Deployment vs. StatefulSet

| Architectural Dimension | Deployment (`apps/v1`) | StatefulSet (`apps/v1`) |
|---|---|---|
| **Naming pattern** | Random alphanumeric hash (`booking-7d6f5c8b-v2k8w`) | Deterministic zero-indexed ordinal (`identity-db-0`, `identity-db-1`) |
| **Pod identity** | Disposable and interchangeable | Persistent and sticky across deletion and recreation |
| **Storage lifecycle** | Ephemeral (`emptyDir`) or shared network volumes | Dedicated, independent PVC per replica generated by `volumeClaimTemplates` |
| **Storage re-attachment** | Replacement Pod gets fresh empty volume | Replacement Pod deterministically rebinds to the ordinal's existing PVC |
| **Startup ordering** | Unordered / parallel creation (governed by surge) | Strict sequential ordering (`0` $\rightarrow$ `1` $\rightarrow$ `2`); waits for preceding Pod to be `Ready` |
| **Teardown ordering** | Unordered / parallel termination | Strict reverse sequential termination (`2` $\rightarrow$ `1` $\rightarrow$ `0`) |
| **Networking model** | Single virtual IP (ClusterIP) load balancing across backends | Companion Headless Service publishing distinct DNS `A` records per ordinal |
| **Network identity** | Callers target virtual Service IP | Callers can target individual Pods: `<pod-name>.<service-name>.<ns>.svc.cluster.local` |

## StatefulSet anatomy: from manifest to physical disk

Let's dissect the core architecture of Apollo's `identity-db` StatefulSet:

~~~yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: identity-db
  namespace: apollo-airlines-apps
spec:
  serviceName: identity-db-headless
  replicas: 2
  podManagementPolicy: OrderedReady
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0
  selector:
    matchLabels:
      app: identity-db
  template:
    metadata:
      labels:
        app: identity-db
    spec:
      containers:
        - name: postgres
          image: postgres:15-alpine
          env:
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          volumeMounts:
            - name: pg-data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: pg-data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: standard
        resources:
          requests:
            storage: 1Gi
~~~

## 1. `volumeClaimTemplates`: per-replica sticky storage

In a standard Deployment, placing a `persistentVolumeClaim` inside `spec.template.spec.volumes` causes **all replicas to mount the exact same PVC**. For block storage (`ReadWriteOnce`), replica 2 fails to schedule because the volume is already locked by replica 1.

`volumeClaimTemplates` fixes this by making storage generation a first-class controller function:
- **Formulaic naming**: For StatefulSet `<name>` with template `<claimName>`, the controller creates PVCs matching `<claimName>-<name>-<ordinal>`.
  - Replicas: 2 $\rightarrow$ creates `pg-data-identity-db-0` and `pg-data-identity-db-1`.
- **Decoupled lifecycle**: The PVC is **not owned** by the Pod. If `identity-db-0` is deleted or crashes:
  - The Pod is destroyed.
  - The PVC `pg-data-identity-db-0` remains completely intact in the cluster with status `Bound`.
  - When the StatefulSet controller creates the replacement `identity-db-0`, the new Pod mounts the existing `pg-data-identity-db-0` PVC.
- **Why PGDATA uses a subdirectory**:
  - PostgreSQL refuses to initialize a database cluster if the target directory contains existing files. Because Linux ext4/XFS filesystems create a `lost+found` directory at volume root, setting `PGDATA=/var/lib/postgresql/data` causes initialization to fail with `directory is not empty`.
  - Apollo sets `PGDATA=/var/lib/postgresql/data/pgdata`, isolating the database engine inside a clean subfolder.

## 2. Headless Services: direct per-Pod DNS identity

Traditional Kubernetes Services act as layer-4 proxies. They allocate a virtual IP (ClusterIP) and route packets across endpoints using round-robin iptables rules.

For clustered databases, routing to a random node fails:
- Database clients executing writes **must** reach the primary.
- Standby replicas configuring streaming replication need to open a direct, persistent TCP connection to the primary's physical IP.

### How a Headless Service works
Declaring `clusterIP: None` disables the virtual IP proxy:

~~~yaml
apiVersion: v1
kind: Service
metadata:
  name: identity-db-headless
  namespace: apollo-airlines-apps
spec:
  clusterIP: None
  selector:
    app: identity-db
  ports:
    - name: postgres
      port: 5432
      targetPort: 5432
~~~

CoreDNS alters its response format when querying headless services:
- **Lookup on the Headless Service**: Resolving `identity-db-headless.apollo-airlines-apps.svc.cluster.local` returns multiple `A` records containing the **direct Pod IPs** of all ready replicas:
  ```text
  identity-db-headless.apollo-airlines-apps.svc.cluster.local. 30 IN A 10.244.1.15
  identity-db-headless.apollo-airlines-apps.svc.cluster.local. 30 IN A 10.244.2.22
  ```
- **Direct Per-Pod FQDN**: When `spec.serviceName: identity-db-headless` is linked in the StatefulSet, CoreDNS generates deterministic per-pod DNS records:
  ```text
  <pod-name>.<service-name>.<namespace>.svc.cluster.local
  ```
  - `identity-db-0.identity-db-headless.apollo-airlines-apps.svc.cluster.local` $\rightarrow$ `10.244.1.15`
  - `identity-db-1.identity-db-headless.apollo-airlines-apps.svc.cluster.local` $\rightarrow$ `10.244.2.22`

> **The Power of DNS Identity**: If `identity-db-0` is evicted to another node and assigned a new IP (`10.244.1.88`), CoreDNS automatically updates the `A` record. Standby replicas and applications that connect to `identity-db-0.identity-db-headless` reconnect successfully without configuration changes.

## 3. Sequential ordering vs. `Parallel` management

By default, StatefulSets enforce `podManagementPolicy: OrderedReady`:

- **Startup Sequence ($0 \rightarrow N-1$)**:
  - `identity-db-0` is created first.
  - `identity-db-1` is created **only after** `identity-db-0` reaches the `Running` state and passes all readiness probes.
  - This guarantees primary databases initialize schemas before standbys attempt replication joins.
- **Teardown Sequence ($N-1 \rightarrow 0$)**:
  - When scaling down from 3 to 1 replicas, `identity-db-2` is completely terminated and removed before `identity-db-1` receives shutdown signals.
  - This prevents split-brain quorum losses in consensus clusters (e.g. etcd, ZooKeeper).
- **Alternative (`podManagementPolicy: Parallel`)**:
  - Launches and terminates all Pods concurrently. Useful for stateful workloads that have independent peer discovery (such as Cassandra or Couchbase) and do not need serialized startup.

## 4. Rolling update partitions and canary releases

Deployments support `maxSurge` and `maxUnavailable`. StatefulSets cannot surge, because each ordinal identity can only exist once.

Instead, StatefulSets update in reverse ordinal order (`N-1` down to `0`), and support **canary rollouts** via `spec.updateStrategy.rollingUpdate.partition`:

~~~yaml
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 2
~~~

- **How partition works**:
  - Any Pod with an ordinal **greater than or equal to** the partition number is updated to the new template.
  - Any Pod with an ordinal **less than** the partition number is left untouched on the old version.
  - *Example*: In a 3-replica cluster (`0`, `1`, `2`), setting `partition: 2` updates only `identity-db-2`. Pods `0` and `1` continue running the old version. Once `identity-db-2` is verified healthy in production, decreasing `partition: 0` finishes updating the remaining replicas.

## 5. PVC retention policy on scale-down and deletion

In Kubernetes 1.27+, the `persistentVolumeClaimRetentionPolicy` controls whether PVCs are deleted or retained during lifecycle events:

~~~yaml
spec:
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain
    whenScaled: Delete
~~~

- **`whenDeleted`**:
  - `Retain` (default): Deleting the StatefulSet object (`kubectl delete statefulset identity-db`) keeps all PVCs intact on disk.
  - `Delete`: Deleting the StatefulSet deletes all child PVCs generated by its template.
- **`whenScaled`**:
  - `Retain` (default): Scaling from 3 replicas to 1 replica preserves `pg-data-identity-db-2`. If you scale back up to 3 tomorrow, the Pod remounts its historical data.
  - `Delete`: Scaling down immediately deletes the discarded ordinals' PVCs, reclaiming storage automatically.

## When NOT to use a StatefulSet

StatefulSets introduce strict operational constraints:
- They do not support `maxSurge` (updates take longer).
- Pod deletion requires sequential teardown by default.
- Storage scaling requires resizing PVCs individually.

**Do NOT use a StatefulSet if:**
- Your application is a stateless HTTP API (use a `Deployment`).
- Your database is a managed cloud service like AWS RDS, Aurora, or Cloud SQL (the cloud provider handles disks and replicas outside Kubernetes).
- Your cache (e.g. Redis) is purely ephemeral and does not persist state to disk between updates.

## Hands-on evidence ladder

Execute these systematic checks to verify StatefulSet mechanics in a live cluster:

- **1. Verify deterministic ordinals**:
  ```bash
  kubectl get pods -n apollo-airlines-apps -l app=identity-db -o wide
  # Expected: identity-db-0, identity-db-1
  ```
- **2. Confirm sticky PVC binding**:
  ```bash
  kubectl get pvc -n apollo-airlines-apps -l app=identity-db
  # Expected: pg-data-identity-db-0 showing Bound
  ```
- **3. Test direct per-pod DNS resolution**:
  ```bash
  kubectl exec -n apollo-airlines-apps deploy/identity -- \
    nslookup identity-db-0.identity-db-headless.apollo-airlines-apps
  # Expected: Resolves directly to identity-db-0's Pod IP
  ```
- **4. Test volume persistence across Pod deletion**:
  ```bash
  # Delete the active database pod
  kubectl delete pod identity-db-0 -n apollo-airlines-apps

  # Watch the controller recreate the identical ordinal
  kubectl get pods -n apollo-airlines-apps -l app=identity-db -w

  # Confirm previous database records survived in PostgreSQL
  kubectl exec -n apollo-airlines-apps statefulset/identity-db -- \
    psql -U postgres -d identity -c "SELECT count(*) FROM users;"
  ```
